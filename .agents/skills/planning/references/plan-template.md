# Implementation Plan

Use these sections as a guide. Omit irrelevant sections and use a short numbered list for a small task. Replace guidance with task-specific findings; do not leave empty headings or unresolved template text in the delivered plan.

## Outcome and acceptance

Describe the requested observable behavior and the criteria that establish completion. Preserve any user-provided acceptance criteria.

## Scope and constraints

State what changes, what remains outside the task, and the constraints that influence the approach.

## Evidence and assumptions

Identify inspected files or other evidence that support the approach. Separate confirmed facts from assumptions. Mark new paths as proposed.

## Decisions or prerequisites

List only unresolved decisions or prerequisites that matter. Explain which steps depend on each one and whether independent work can proceed. Omit this section if there are none.

## Implementation steps

For each step, provide:

- Outcome: the concrete change or decision.
- Affected area: inspected files or components, or explicitly proposed new files.
- Dependencies: earlier steps or external prerequisites, if any.
- Completion check: the observable result that makes the step complete.

Use numbered steps in execution order. For conditional work, state the condition explicitly.

## Validation

Connect acceptance criteria to planned tests or manual checks. Include supported commands and environment requirements when known. Distinguish planned checks from investigation checks already executed and report actual results only for executed checks.

## Risks and recovery

Include only material risks, with their conditions, impact, and response. Describe rollout order or recovery when relevant to the change.

## Next action

Name the first executable step. If a required decision blocks it, identify that decision. If implementation is already authorized, proceed with the actionable work rather than ending with an unnecessary request for permission.
