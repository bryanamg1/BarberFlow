# Feature Specification

Adapt these sections to the feature's size. Replace guidance with task-specific content and omit sections that do not help implementation. A small feature can be a short description and a few acceptance criteria.

## Problem and outcome

Identify the actor, the current problem, and the intended observable outcome. Include a success measure only when supplied or supported by evidence.

## Scope and exclusions

State required capabilities, explicit constraints, and what is outside this change. List optional suggestions separately from required scope.

## Current behavior and evidence

Summarize relevant inspected behavior and source requirements. Distinguish facts, assumptions, proposed changes, and conflicts between sources. Label uninspected integration points explicitly.

## Actors and business rules

Define relevant actors and the conditions, results, or invariants that govern the feature. Include access scope where it matters. Mark proposed policies as proposals rather than accepted rules.

## Use cases and states

Describe preconditions, action, success outcome, and relevant failure or alternative outcomes. Add a transition table if the feature has a meaningful lifecycle. Distinguish persisted effects from UI feedback and external effects.

## Data and contract expectations

State relevant input, output, validation, and data effects. Note existing interfaces or consumers that constrain the change. Label technical mechanisms as proposals unless mandated.

## Acceptance criteria

List concrete conditions, actions, and observable results. Cover important rules and applicable negative cases. Add identifiers only when they improve traceability. These criteria describe future verification, not tests already passed.

## Open decisions and assumptions

For each material uncertainty, state the question, affected behavior, and whether it blocks implementation. Identify reversible assumptions that permit independent work. Omit this section when no uncertainty remains.

## Readiness and next action

State which behavior is sufficiently specified and what remains blocked. Identify the next executable activity, such as resolving a business decision, inspecting an integration contract, or planning implementation. Continue already-authorized work without an unnecessary request for approval.
